DB RESTRUCTURE PLAN — executed 2026-08-01
=========================================

Sections 1-3 of this plan (unified event_participants table, unified event
teams table, event-type capabilities reference table) plus section 4 are DONE,
in migrations:

  20260802110000_event_type_capabilities.sql
  20260802110001_unify_participants_and_teams.sql
  20260802110002_hardening_cheap_wins.sql
  20260802110003_restrict_player_deletion.sql

Adding a participant-bearing event type now costs one row in `event_types`
plus one member of the `EventType` union in src/types.ts; the compiler
(unhandledEventType) points at every dispatch site that needs a branch.

Verified by `npm run db:test` (scripts/migration-replay.mjs), which replays the
entire migration history against a throwaway Postgres with production-shaped
seed data and asserts the backfill, constraints, RLS and triggers. Run it before
any db:push — it catches what tsc and the Supabase linter cannot, and CI runs it
on every change under supabase/migrations/.

Two deviations from the plan as written, both deliberate:

  * The winner column moved to events.winning_team_id, but mods do NOT get an
    UPDATE policy on events. The old matches/tournaments arrangement (mod
    UPDATE + a BEFORE UPDATE trigger restricting non-admins to one column)
    cannot be lifted onto events: that trigger fires for every writer,
    including the table owner, and is_admin() is false without an end-user
    JWT — so it would reject every future migration and service-role write.
    The winner is set through the SECURITY DEFINER `set_event_winner` RPC
    instead, matching how every other mod/player-scoped write already works.

  * Old tables were dropped in the same migration as the backfill rather than
    a deploy cycle later: everything here ships in one `db push`, so a delayed
    drop would land in the same batch anyway. Count assertions inside the
    transaction abort the whole migration on any mismatch.


DECIDED 2026-08-02
------------------

1. Social-event visibility — DECIDED: leave as is. events and locations stay
   anon-readable. Checked at the time: all 18 locations were named commercial
   venues (clubs, predios, polideportivos) and the only social event was at
   Club Comunicaciones, so nothing private was exposed. The residual risk is a
   future social event at a private address, where the name, the exact date and
   time, and the maps pin would be readable while logged out. If that ever
   matters, the fix is one policy on events:
   `type <> 'social' OR auth.role() = 'authenticated'`.

2. Player deletion — DONE in 20260802110003, but NOT via soft-delete.
   event_participants.player_id and media_player_tags.player_id became
   ON DELETE RESTRICT, joining event_award_resolutions (20260802100001), and a
   BEFORE DELETE trigger on players explains the refusal in Spanish (PlantelPage
   alerts error.message straight to the admin). Deleting a player with history
   is now refused instead of silently erasing it; a player with no history at
   all still deletes.

   Soft-delete (players.deleted_at) was rejected: it taxes every player query,
   players_public, the roster UI and the unique-name constraint forever, and it
   solves a problem nobody has — deleting someone while KEEPING their history.
   The real defect was that the erasure was SILENT. Revisit only if preserving
   a deleted player's record becomes an actual requirement.

   Live data at the time: of 56 players, 39 already held an award and were
   protected; 16 of the remaining 17 had real history (up to 6 appearances and
   5 photo tags) that one confirm dialog would have wiped.

Consciously decided NOT to do (recorded so they aren't re-litigated):

  * Team-name uniqueness within an event: duplicates are immediately visible
    user error and every relation keys on team ids, so a constraint would add
    friction without preventing a real failure.
  * created_by audit columns: these tables are world-readable, so recording
    the author would let anyone enumerate which players are mods/admins —
    which 20260417120000 deliberately hides. Real actor attribution needs an
    RLS-gated audit table; created_at alone was added everywhere instead.
